**The CMS boundary.** For every meaningful piece of frontend-visible content: what becomes backend-managed, and what stays frontend code.

Derived by reading `svfrontend/src/` in full. **This is the primary implementation reference for scope.**

## Classification key

| Class | Meaning |
|---|---|
| **ADMIN** | Admin-editable. Lives in the database, served by the API |
| **STATIC** | Stays in frontend code. Structural, design, or editorial-voice content a developer owns |
| **SYSTEM** | Generated by the system or by users; not authored |
| **FUTURE** | Justified but deferred. Not in the first build |
| **UNCERTAIN** | Needs an owner decision — see `OPEN-QUESTIONS.md` |

**Tier** — T1 = build first · T2 = build once T1 is stable · T3 = not building.

## The governing test

> *"Would the business owner reasonably expect to change this without a developer?"*

A phone number: **yes** → ADMIN. A headline's italic line break: **no** → STATIC.

### Deliberately NOT modelled

- **`Service` entity** — the brief says "services"; the frontend has none. What exists is infrastructure *specifications* and *benefits*. Do not create it. (OQ-13)
- **`Article` / blog** — documented in README and PRD, but the route does not exist and 404s. (OQ-14)
- **Plot inventory, per-plot pricing, floor plans, possession dates, structured RERA/DTCP numbers** — no frontend evidence. The repo explicitly records that none were supplied.
- **Public user accounts** — zero evidence.
