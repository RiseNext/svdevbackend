**Principle: proportional architecture.** Single-digit projects, tens of leads per month, one admin role. That is a **single service with a single database** — not microservices, not a message bus, not a cache tier beyond what the frontend already does.

## 3. Internal layering

**Superseded by D-015.** The layering below was written for a hand-built Fastify service. Payload does not have routes/services/repositories, and imposing that shape on it fights the framework.

**The actual file map is [`MASTER-IMPLEMENTATION-PLAN.md`](./MASTER-IMPLEMENTATION-PLAN.md) §21.** In outline: `src/collections/` and `src/globals/` (config-as-code) · `src/access/` · `src/hooks/` · `src/app/(payload)/` (admin + Payload's own API) · `src/app/(public)/api/v1/` (our hand-written public Route Handlers) · `src/serializers/` · `src/schemas/` (Zod) · `src/jobs/` · `src/migrations/` · `src/seed/`.
*(`src/email/` was deleted on 21 Sep 2026 with the email subsystem.)*

**The rule that survives, restated for Payload:** *a public Route Handler never returns a Payload document directly.* It calls the Local API and passes the result through an allow-list serialiser, built key by key, never spread. That is the same separation the old rule protected — authorization and response shaping in one place — expressed in the framework we actually use.

## 4. Frontend integration — the decision that matters most

The public site is **15 statically prerendered pages** *(corrected from “17”, 20 Sep 2026)* with a First Load JS of 102–114 kB and LCP < 2.5 s. Naively fetching from the backend on every request would convert every page to SSR and **destroy those numbers** (NFR-02, NFR-03).

**Recommended: ISR + on-demand revalidation.**

```
Build / revalidate:  Next.js ─fetch─► Public API ─► renders static HTML
Visitor request:     Visitor ─────► CDN (static HTML) ─── backend not involved
Admin publishes:     Admin ─► Admin API ─► DB ─► POST /api/revalidate ─► Next rebuilds affected paths
```

Consequences:
- Visitors never wait on the backend. Backend downtime leaves the site serving the last good build (NFR-02).
- `generateStaticParams` in `app/projects/[slug]/page.tsx` feeds from `GET /projects` instead of the static array.
- Publishing must trigger revalidation (FR-PUB-10) or edits never appear. Needs a shared secret.
- **`POST /api/v1/leads` is the one live call from a visitor's browser** — so it is the only place CORS matters for public traffic.

**Rejected:** client-side fetching (destroys SEO and LCP for a content site), full SSR (ties public uptime to the backend), backend-renders-HTML (throws away the entire existing frontend).

## 5. Request flows

**Public read (build time)** → Next build → `GET /api/v1/projects` → service → repo → Postgres → published rows only → static HTML.

**Lead submit (live)** → browser `POST /api/v1/leads` → CORS check → rate limit → honeypot → Zod validate → verify `projectSlug` exists → persist → **enqueue** notification → `201`. Notification failure never fails the request (FR-LEAD-06).

**Admin mutation** → cookie → session lookup → authorize → Zod validate → service → transaction → **audit write** → optional revalidation hook → `200`.

## 6. Authentication design

**Recommended: server-side sessions in an httpOnly, Secure, SameSite=Lax cookie.**

Rationale: the admin UI is a browser app on a known origin. Sessions are revocable server-side the instant an account is disabled — a stateless JWT is not, without building a denylist that re-introduces the state JWT was meant to avoid. There is no mobile client and no third-party consumer to justify bearer tokens.

- Session record: `id`, `admin_user_id`, `expires_at`, `created_at`, `last_seen_at`, `ip`, `user_agent`.
- Sliding expiry with an absolute cap.
- Logout deletes the row. Password change invalidates all other sessions.
- CSRF: `SameSite=Lax` plus an origin check on mutations. See `SECURITY.md`.

**If** a JWT is chosen instead: short-lived access token + rotating refresh token, refresh stored server-side so revocation still works. Record the choice in `DECISIONS.md`.

## 8. Deployment

Frontend and backend deploy **independently**. Frontend is Vercel-shaped (static output). Backend is a long-running Node process — any container host or PaaS.

CORS is a strict allow-list of exactly two origins: the public site (for `POST /leads` only) and the admin UI. **Never `*`** — the admin API is cookie-authenticated, and a wildcard with credentials is an open door.

## 9. What is deliberately absent

| Not building | Why |
|---|---|
| Microservices | One service, one database, one team |
| Message queue (external) | A DB-backed job table covers the one async task (notifications) |
| Redis / cache tier | ISR is the cache. Add only if measurement demands it |
| GraphQL | Handful of fixed, well-known shapes |
| Realtime / WebSockets | Nothing in the UI needs live updates |
| Search service | 5 projects, filtered client-side |
| CDN for API | Public reads happen at build time, not per visitor |
